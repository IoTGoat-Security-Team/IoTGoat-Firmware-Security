# OWASP IoTGoat 3주차 동적 분석 실습 보고서

## 1. 실습 개요

* **실습 목적:** 정적 분석에서 식별한 `shellback` 바이너리의 인증 부재 원격 셸 취약점(CWE-306)을 격리된 에뮬레이션 환경에서 동적으로 검증하고, 디버거(GDB)를 통해 어셈블리 명령어 및 주요 시스템 콜(`socket`~`execve`) 수준에서 백도어의 동작 원리를 증명한다.
* **분석 대상:** OWASP IoTGoat (Raspberry Pi 2 펌웨어) 내 `/usr/bin/shellback` (ARM 32-bit ELF, Stripped)
* **실습 환경:**
  * Host OS: Ubuntu Linux (VM 격리 환경)
  * Emulation: `qemu-arm-static` + `chroot` (유저 모드 격리 실행)
  * Debugging / Network Tools: `gdb-multiarch`, `nc` (Netcat), `ss`
* **분석 관점 분담 및 통합:**
  * **보안 취약점 및 권한 검증:** 격리 환경 구성, 포트 개방 및 원격 접속 테스트, `root` vs `nobody` 권한별 비교, 중요 파일(`/etc/shadow`) 권한 결함 검증 및 대응 방안 도출
  * **GDB 심층 동적 해부:** ARM 어셈블리 단계별 실행(`stepi`), 레지스터·스택 변화 추적, 네트워크 소켓(`FD`)·프로세스 분기(`fork`)·입출력 복제(`dup2`)·셸 실행(`execve`) 전 과정 검증

## 2. 동적 분석 5단계 수행 내용

### 2.1 [1단계] 격리된 VM/QEMU에서 대상 실행 및 스냅샷 확보

외부 네트워크 및 호스트 시스템에 영향을 주지 않도록 가상 머신 스냅샷을 확보한 뒤, 추출된 펌웨어 파일시스템(`squashfs-root`)을 `chroot`로 격리하고 `qemu-arm-static`을 통해 ARM 바이너리를 실행하였다.

* **실행 절차:**
  ```bash
  cd ~/IoTGoat-raspberry-pi2/_IoTGoat-raspberry-pi2.img.extracted/squashfs-root
  sudo cp /usr/bin/qemu-arm-static ./usr/bin/
  sudo chroot . /usr/bin/qemu-arm-static /usr/bin/shellback
  ```
* **환경 분리 의미:** 터미널 1(`sudo chroot`)은 부팅 시 `root` 권한으로 `shellback`이 상시 실행되는 피해 IoT 기기를 재현하며, 터미널 2(일반 계정 `nc`)는 사전 권한이 없는 외부 접속자를 재현한다.

---

### 2.2 [2단계] 정상 입력의 기준 동작과 로그 기록

외부 접속을 시도하기 전, `shellback` 프로세스가 시스템에서 어떤 네트워크 포트를 개방하고 대기하는지 기준 상태를 기록하였다.

* **확인 명령어 및 결과:**
  ```text
  $ ss -tlpn | grep 5515
  LISTEN   0   1   0.0.0.0:5515   0.0.0.0:*
  ```
* **기준 동작 분석:** 프로그램 실행 즉시 모든 네트워크 인터페이스(`0.0.0.0`)의 TCP `5515` 포트가 `LISTEN` 상태로 개방되어, 외부 어느 IP(`0.0.0.0:*`)에서 오는 연결이든 상시 대기함을 확인하였다.

---

### 2.3 [3단계] 공식 교육용 시나리오 검증 및 권한별 비교 실험

`nc`를 이용해 `127.0.0.1:5515` 포트에 접속하여 인증 절차 존재 여부를 확인하고, 실행 권한을 `root(uid=0)`와 `nobody(uid=65534)`로 달리하여 피해 범위와 추가 취약점을 비교 검증하였다.

#### ① 최고 관리자(`root`, uid=0) 실행 시 (실제 기기 기본 상태)
* **검증 결과:**
  ```text
  $ nc -v 127.0.0.1 5515
  Connection to 127.0.0.1 5515 port [tcp/*] succeeded!
  [***]Successfully Connected to IoTGoat's Backdoor[***]
  id
  uid=0(root) gid=0(root) groups=0(root)
  echo $?
  0
  ```
* **분석:** 아이디·비밀번호 입력이나 인증 토큰 없이 접속 즉시 백도어 배너가 출력되며, 권한 하향(Drop privilege) 없이 최고 관리자(`root`) 권한의 셸이 제공되었다.

#### ② 최저 권한(`nobody`, uid=65534) 비교 실험
* **실행 명령어:**
  ```bash
  sudo chroot --userspec=65534:65534 . /usr/bin/qemu-arm-static /usr/bin/shellback
  ```
* **검증 결과:**
  * `id` 실행 시 `uid=65534(nobody) gid=65534(nogroup)`으로 원격 셸이 여전히 인증 없이 개방됨을 확인하였다.
  * SUID 파일 점검(`find / -perm -4000`) 결과 SUID 설정 바이너리는 존재하지 않았다.
  * 중요 계정 파일 권한 점검(`ls -l /etc/passwd /etc/shadow`) 결과:
    ```text
    -rw-r--r-- 1 iotgoatu 1000 284 Jan 30 2019 /etc/passwd
    -rw-r--r-- 1 iotgoatu 1000 269 Jan 30 2019 /etc/shadow
    ```

* **권한별 비교 실험 결론:**

| 구분 | `root` (uid=0) 실험 | `nobody` (uid=65534) 실험 |
| :--- | :--- | :--- |
| **핵심 취약점** | CWE-306 (인증 없는 원격 셸 개방) | CWE-306 (권한을 낮춰도 동일하게 뚫림) |
| **추가 문제점** | Drop privilege 미적용 (즉시 시스템 장악) | CWE-732 (`/etc/shadow` 읽기 권한 `644` 노출) |
| **영향도** | 파일 삭제, 설정 변조 등 시스템 완전 제어 | 민감 정보(비밀번호 해시) 열람 및 오프라인 크래킹 연계 가능 |

#### ③ 정상(보안 기준) vs 비정상(실습 검증) 동작 비교표

| 비교 항목 | 정상 동작 (보안 기준 / 예상 동작) | 비정상 동작 (실습 검증 결과) | 판정 및 관련 CWE |
| :--- | :--- | :--- | :--- |
| **네트워크 포트 개방** (`ss -tlpn`) | 인가된 관리 포트(SSH 등)만 제한적으로 개방 | 모든 인터페이스(`0.0.0.0:5515`)에서 백도어 포트 상시 `LISTEN` | 비정상 (불필요 포트 노출) |
| **원격 접속 시 인증** (`nc 127.0.0.1 5515`) | ID/PW 또는 키 인증 요구, 미인증 시 연결 종료 | 인증 절차 없이 즉시 `[***]Successfully Connected...` 배너 출력 | 취약 (**CWE-306**) |
| **원격 셸 및 권한** (`id`, `echo $?`) | 미인증 외부인의 명령 실행 불가 (오류 반환) | 무인증 접속 직후 `uid=0(root)` 셸 획득, 명령 정상 실행(`$? = 0`) | 취약 (**CWE-306**, 최소 권한 위배) |
| **최저 권한 실행 시** (`nobody`, `65534`) | 비인가 접근 차단 및 셸 실행 거부 | 권한을 `nobody`로 낮춰도 인증 없이 원격 셸 개방 유지 | 취약 (**CWE-306**) |
| **내부 시스템 콜** (`GDB`) | 인증 검증 루틴 통과 후 제한된 서비스 프로세스 실행 | `accept` 직후 `dup2`로 입출력 연결 및 `execve("/bin/busybox", ["sh"])` 직접 호출 | 취약 (백도어 실행 증명) |
| **중요 파일 접근** (`/etc/shadow`) | `600` (`-rw-------`) 권한으로 `root` 외 접근 거부 | `644` (`-rw-r--r--`) 권한으로 `nobody` 계정에서도 해시 열람 가능 | 취약 (**CWE-732**) |

### 2.4 [4단계] GDB 원격 디버깅 및 함수·어셈블리 심층 분석

`qemu-arm-static -g 1234` 옵션으로 원격 디버깅 서버를 열고 `gdb-multiarch`를 연동하여, ARM 어셈블리 명령어의 단계별 실행과 주요 함수 호출(`htons` → `socket` → `bind` → `listen` → `accept` → `fork` → `write` → `dup2` → `execve`) 전 과정을 레지스터 및 메모리 수준에서 추적하였다.
*(함수 호출 전 ARM 레지스터 `r0`~`r3`에서 인수를 확인하고, 복귀 후 반환값은 `r0`에서 확인하였다.)*

#### ① 디버거 연동 및 핵심 중단점 설정
```gdb
(gdb) target remote :1234
(gdb) b *0x10588        # main 함수 진입 지점
(gdb) b *0x1063c        # execve 호출 직전 지점
(gdb) c
```

#### ② ARM 명령어 한 단계 실행(`stepi`)과 레지스터·스택 변화
`x/i $pc`로 현재 명령어를 확인하고 `stepi`로 한 명령어씩 실행하며, `info registers`와 `x/3wx`로 레지스터(`pc`, `sp`, `lr` 등) 및 메모리 32비트 값의 변화를 관찰하였다.

| 명령어 | 관찰된 동작 및 레지스터·메모리 변화 |
| :--- | :--- |
| **`LDR`** | 메모리에서 값을 로드. 첫 `LDR` 실행 후 `r3`에 `0x10740`, 이후 `LDR` 실행 후 `r9`에 안내 문구 주소 `0x1074c`가 적재됨. |
| **`PUSH`** | `r4`~`r10`과 `lr` (32비트 레지스터 8개, 총 32바이트)을 스택에 저장. |
| **`SUB`** | `sub sp, sp, #48` 실행 후 `sp`가 `0x407fff48`에서 `0x407fff18`로 감소하여 스택에 지역 데이터용 공간 48바이트 확보. |
| **`LDM`** | `r3`가 가리키는 메모리에서 3개의 값을 한꺼번에 읽어 `r0`, `r1`, `r2`에 적재. |
| **`ADD`** | `add r6, sp, #4` 실행 후 `r6`은 `0x407fff1c`로 설정됨 (`sp`는 유지). |
| **`MOV`** | `r5` 레지스터에 상수 `2`를 대입. |
| **`STM`** | 앞서 `LDM`으로 읽은 세 값을 `r6`이 가리키는 스택 공간에 연속 저장 (이후 이 메모리 영역에서 BusyBox 실행 인수 배열 확인). |
| **`CMP` / `BEQ`** | `cmp r0, #0`으로 `fork()` 반환값을 0과 비교. 부모 프로세스의 `r0`가 `2948`이므로 `beq` 분기가 발생하지 않고 다음 명령어로 진행. |

#### ③ 주요 함수 호출별 동적 동작 추적

1. **접속 준비 및 수락 (`htons` → `socket` → `bind` → `listen` → `accept`)**
   * `htons()`: 호출 전후 `r0` 값을 비교한 결과 포트 번호의 두 바이트 순서가 바뀌어 네트워크 바이트 순서(상위 바이트 먼저)로 메모리에 저장됨을 확인하였다.
   * `socket()`: IPv4 TCP 소켓을 생성하고 파일 디스크립터 **`FD 5`**를 반환하였다.
   * `bind()` / `listen()`: `FD 5`에 로컬 주소와 포트를 할당하고 접속 대기 상태로 전환하였으며, 두 함수 모두 성공을 뜻하는 **`0`**을 반환하였다.
   * `accept()`: 외부 접속을 수락한 뒤 새 연결용 **`FD 6`**을 반환하였다. (`FD 5`는 대기용, `FD 6`은 실제 클라이언트 데이터 송수신용)

2. **프로세스 분기 및 안내 문구 전송 (`fork` → `write`)**
   * `fork()`: 호출 후 부모 프로세스의 `r0`에서 새로 생성된 자식 프로세스 번호(PID) **`2948`**을 확인하였다. 부모는 반환값이 0일 때의 분기를 건너뛰고 `write()`로 진행하였다.
   * `write()`: 지정한 길이 **55바이트**에 대해 호출 후 `r0`에서도 **`55`**가 반환되어, 백도어 접속 안내 문구 55바이트가 연결 소켓(`FD 6`)에 모두 전송되었음을 확인하였다.

3. **표준 입력·출력·오류 리다이렉션 (`dup2`)**
   * `dup2()` 호출 전 `r0`는 세 번 모두 연결 소켓을 가리키는 **`FD 6`**이었으며, `r1`에 복제 대상 번호(`0`, `1`, `2`)를 전달하여 매번 해당 대상 번호가 `r0`로 반환됨을 확인하였다.

| 구분 | 대상 번호 (`r1`) | 반환값 (`r0`) | 보안 및 동작 의미 |
| :--- | :---: | :---: | :--- |
| **표준 입력 (`stdin`)** | `0` | `0` | 셸이 연결 소켓(`FD 6`)으로부터 원격 명령을 수신 |
| **표준 출력 (`stdout`)** | `1` | `1` | 명령 실행 결과가 같은 소켓(`FD 6`)으로 전송 |
| **표준 오류 (`stderr`)** | `2` | `2` | 오류 메시지도 같은 소켓(`FD 6`)으로 전송 |

#### ④ `execve()` 인자 검증 및 원격 셸 응답 증적 (`0x1063c`)
`execve(pathname, argv, envp)` 호출 직전 중단점(`0x1063c`)에서 `$r0`(단일 포인터, `char *`)와 `$r1`(이중 포인터, `char **`)을 역참조하여 실행 대상을 확인하였다.

```gdb
(gdb) x/s $r0
-> "/bin/busybox"          # 실행할 바이너리 경로 (pathname)

(gdb) x/s *(char **)$r1
-> "/bin/busybox"          # argv[0]

(gdb) x/s *((char **)$r1 + 1)
-> "sh"                    # argv[1] (셸 실행 인자)
```

* **실행 및 응답 증적:**
  * `execve` 실행 직후 GDB에는 **`Remote connection closed`**가 표시되며 제어권이 새 프로세스(`/bin/busybox sh`)로 전환되었다.
  * 동시에 연결되어 있던 Netcat(`nc`) 창에서 시험 명령을 입력했을 때 **`IOTGOAT_EXECVE_OK`** 응답이 한 줄로 정상 반환되었으며, 명령 실행 직후 `echo $?` 출력값 **`0`**을 통해 원격 명령이 오류 없이 처리되고 소켓으로 결과가 돌아옴을 이중으로 증명하였다.

### 2.5 [5단계] 재현 실패 시 실행 환경 문제와 취약점 여부 구분

실습 과정에서 발생한 오류들을 분석하여, 취약점 부재가 아닌 **실행 및 격리 환경의 제약 요인**임을 명확히 분리하였다.

| 발생 오류 및 현상 | 원인 분류 | 상세 분석 및 조치 결과 |
| :--- | :--- | :--- |
| `Connection refused` (5515 포트) | 디버깅 대기 상태 | GDB 연동 전이거나 중단점(`0x10588`)에서 멈춰 포트가 열리지 않은 상태. `target remote :1234` 후 `c`로 실행을 재개하여 해결. |
| `chroot: Operation not permitted` | 호스트 실행 권한 | `chroot` 자체는 관리자 권한이 필요함. `sudo chroot --userspec=65534:65534` 형식으로 격리 후 권한 하향 적용. |

## 3. 식별된 취약점 및 보안 대응 방안

### 3.1 식별된 취약점 요약
1. **CWE-306 (Missing Authentication for Critical Function):** TCP `5515` 포트를 통해 인증 절차 없이 `dup2`와 `execve("/bin/busybox", ["sh"])`로 원격 시스템 셸을 개방하는 백도어 존재.
2. **최소 권한 원칙 위배 (Drop privilege 미적용):** 불필요한 백도어 서비스가 `root` 권한을 낮추지 않고 유지한 채 셸을 제공하여 침투 즉시 기기 전체가 장악됨.
3. **CWE-732 (Incorrect Permission Assignment for Critical Resource):** 계정 비밀번호 해시가 저장된 `/etc/shadow` 파일에 기타 사용자 읽기 권한(`-rw-r--r--`, `644`)이 부여되어 최저 권한(`nobody`)에서도 유출 가능.

## 4. 결론

본 3주차 동적 분석 실습을 통해 `shellback` 바이너리가 외부 접속 수락(`accept`, `FD 6`) 직후 입출력을 소켓에 연결(`dup2`)하고 인증 절차 없이 `/bin/busybox sh`를 실행(`execve`)하는 치명적 백도어 취약점(CWE-306)을 보유하고 있음을 QEMU, Netcat, GDB로 다각도 증명하였다. 또한 어셈블리·시스템 콜 수준의 심층 추적과 더불어 `root` vs `nobody` 권한 비교 실험을 병행함으로써, 권한을 낮추더라도 원격 셸 개방 자체와 `/etc/shadow` 권한 설정 미흡(CWE-732)으로 인한 위험이 상존함을 확인하고 실질적인 보안 대응 방안을 도출하였다.
